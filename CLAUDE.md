# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A PWA for checking the current closure status of the Mt. Rainier pool. It scrapes `mtrainierpool.com`, stores closure messages in Supabase, and runs them through a Supabase AI model (`pool-operator`) to extract structured closure/reopening dates. When a new analysis indicates the pool is closed, it emails registered users via AWS SES.

## Monorepo layout

Two separate runtime stacks share this repo:

- **`frontend/`** — React + Vite PWA (Yarn workspace, Node/browser target)
- **`supabase/functions/api/`** — Hono Edge Function (Deno, runs on Supabase)
- **`scripts/`** — Deno CLI for triggering the edge function and generating the API client

The root `deno.json` manages Deno workspaces (`supabase/functions/api` and `scripts`). The root `package.json` manages the Yarn workspace (`frontend/`).

## Architecture

### Edge Function (`supabase/functions/api/`)

Hono app with `@hono/zod-openapi`. Routes are mounted under `/api` (`index.ts`). Both routes use `@supabase/server` middleware (`withSupabase({ auth: ["secret"] })`) — callers must pass the service role key. Routes extend `DefaultOpenAPIHono` (`utils/hono.ts`), an `OpenAPIHono` subclass whose `defaultHook` logs zod validation failures.

**`GET /api/check`** (`routes/check.ts`):

1. Fetches `https://mtrainierpool.com` and extracts `#updates_banner p` text.
2. UUIDs the banner text (UUID v5 under a custom namespace) to deduplicate — upserts into `pool_updates`.
3. Fires `EdgeRuntime.waitUntil(runPoolOperator(...))` to call the `pool-operator` Supabase AI model, which returns a JSON **array** of closure objects (each with `closure_date`, `reopening_date`, `confidence_score`, `reasoning`, and `flags`). Filters to items that carry a closure or reopening date, then calls the `ingest_pool_operator_analysis` RPC to insert a `pool_operator_analysis` row (1:1 with the update, on conflict of `pool_update_id`) plus its `pool_closures` children in a single transaction.

**`POST /api/notify/email`** (`routes/notify.ts`):

- Takes an `{ analysisId }` body, loads the matching `pool_operator_analysis` together with its `pool_closures` (and the parent `pool_updates` row), and emails every registered user via AWS SES — but only when the analysis has at least one closure (any closure means the pool is closed).
- Uses the `withAws` middleware (`middleware/aws.ts`) to attach an `SESClient` to the Hono context.
- Delivery is idempotent: it upserts a `notification_deliveries` row keyed on `(idempotency_key, user_id)` (idempotency key = analysis id), then atomically claims it by flipping `pending → sending`. Only the claimer sends, then records `sent`/`failed` and writes an `email_deliveries` audit row.

This route is **not** called by cron. A Postgres trigger (`notify_pool_closure_email`, a deferred constraint trigger AFTER INSERT on `pool_operator_analysis`) fires `net.http_post` to it with the new analysis id, but only when that analysis produced at least one `pool_closures` row. It is `DEFERRABLE INITIALLY DEFERRED` so it runs at COMMIT — after `ingest_pool_operator_analysis` has inserted the closures in the same transaction — using `project_url` + `service_role_key` from Vault.

A `pg_cron` job (`pool-check-10min`) calls `GET /api/check` every 10 minutes during the morning PST window (`*/10 9-15 * * *` UTC ≈ 1–8 AM PST) using credentials stored in Supabase Vault.

### Generated API client (`scripts/client/`)

Auto-generated by `@hey-api/openapi-ts` from the live OpenAPI document exported by the Hono app. **Do not hand-edit files in `scripts/client/`** — regenerate with `yarn pool create-client`.

### Frontend

- **UI**: Mantine v9 (dark scheme default), `@tanstack/react-router`, `@tanstack/react-query`
- **Auth**: `SupabaseProvider` in `frontend/src/api/supabase.tsx` wraps the whole app; exposes `useAuth()`. The router context carries `auth` and `queryClient`.
- **Route tree**: Generated by the TanStack Router Vite plugin — **do not edit `src/routeTree.gen.ts` manually**. Add routes as files under `src/routes/`.
- **Auth-gated routes**: Files prefixed `_auth` (e.g., `_auth.home.tsx`) live under the `_auth` layout route, which redirects unauthenticated users to `/login`.
- **Data fetching**: `queryOptions` objects in `src/api/` are passed to `useQuery`. Stale time is 1 hour for pool data.
- **Notifications**: `usePoolNotifications()` (`src/hooks.ts`) requests notification permission and posts a `TRIGGER_CHECK` message to the service worker (`src/sw.ts`) on load and when the tab regains focus. The worker (`checkForNewAnalysis`) fetches the latest `pool_operator_analysis` (with its `pool_closures`) and shows a local notification if it has any closures, deduped against the last-seen analysis id cached in `pool-sync-state`.

### Database schema (public)

- `pool_updates` — raw scrape results: `id` (UUID v5), `message`, `source`, timestamps
- `pool_operator_analysis` — one LLM analysis per pool update, linked 1:1 via `pool_update_id` (unique): `model`, timestamps. The structured closure data lives in child `pool_closures` rows.
- `pool_closures` — zero or more closures extracted from an analysis (FK `analysis_id` → `pool_operator_analysis`): `closed_at`, `opened_at`, `confidence_score`, `reasoning`, `flags[]`. Presence of any row means the pool is closed.
- `notification_deliveries` — one row per (notification, user) delivery attempt: `type`, `channel` (`email`/`sms`), `status` (`pending`→`sending`→`sent`/`delivered`/`failed`/`cancelled`), `idempotency_key`, `recipient`, `provider`, `attempts`, timestamps. Unique on `(idempotency_key, user_id)`.
- `email_deliveries` — email-specific audit/event detail (bounce/complaint) linked 1:1 to a `notification_deliveries` row via `delivery_id`

RLS is auto-enabled on all `public` tables via an event trigger (`rls_auto_enable`).
